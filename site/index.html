Know what is safe to remove.

PruneDisk is a free, open-source disk analyzer for developer machines. Today a read-only command-line tool scans a disk, works out what each folder is (a git repo, a worktree, a rebuildable folder, a cache) and plans what could be removed, backed up first, or left alone. It deletes nothing. It is being built into a cleaner for Windows, macOS and Linux, which are the target platforms: the project's automated build and tests run on all three.

The problem

A developer disk fills up in a particular way. Hundreds of clones. Linked worktrees an agent created and never tidied. A node_modules or target folder in every project you have ever touched. Package caches. Gigabytes of coding-agent transcripts and logs. Rendered videos and model files that were never meant to go into git.

A general disk tool shows you one big folder and leaves the judgment to you. The risky part is that the folder next to it may hold the only copy of an unpushed branch, a stash, or a .env file. PruneDisk is being built to tell those cases apart before anything is touched.

How it decides what is safe

Every directory gets one class. The classes come from the project's design document; the read-only scanner assigns repo, worktree, bare-repo, regenerable, cache and loose-code (everything else is "other"), and lists output files individually. Agent-session handling is designed but not built. The last column says what today's plan proposes for an idle project; what the design adds later is marked Planned. Nothing is removed yet: the step that applies a plan is planned too.

ClassWhat it isToday's plan

worktreeA linked git worktree.Like a repo, checked against its own HEAD.
bare-repoA bare git repository.Keep while a worktree or clone depends on it; otherwise ask.

loose-codeSource files or a project manifest outside any repo.Ask: connect a remote, back up, remove, or leave.
system, user-dataOperating system files, documents, photos.Keep: analysis only. Today these count as "other".

What it checks before it calls a repo safe

For every repo and worktree the scanner records eleven facts. Each is yes, no or unknown. Unknown never counts as yes: a check that fails or times out leaves the fact unknown, and an unknown fact never leads the plan to propose removal; for an idle repo it asks you instead.

  • It has at least one network remote. A local path or a bundle file is not a backup.
  • The checked-out commit is on a remote branch, including a detached HEAD.
  • Every local branch is on a remote. A repo with local tags stays unknown until the remote itself is asked.
  • The stash is empty.
  • The working tree is clean: no changes and no untracked files.
  • There are no ignored files that exist only here, such as .env or a local database.
  • No other clone or worktree depends on this one.
  • Every commit the reflogs still remember, such as one left behind by a reset or a rebase, is on a remote.
  • No rebase, merge, cherry-pick, revert or bisect is half finished, and the git directory holds no Git LFS or git-annex objects, which may exist only here.
  • The repository has a plain layout, with nothing unusual in its git directory.
  • The git directory holds nothing of its own, such as a custom hook or a setting only this copy has.

For an idle repo the plan proposes backup-then-remove when all eleven are yes: back up its git directory, then remove it. When some facts are no and none is unknown, it proposes recover-backup-then-remove: recover the missing work first, then back up and remove. When any fact is unknown, or the repo has dependents, an unusual layout or files of its own in its git directory, it asks you (ask). It also asks when git is told to hide edits to some files (skip-worktree or assume-unchanged), even if every fact is yes. It always says why. Remote facts come from local remote-tracking refs, which can be stale, so the plan marks them unverified. Re-checking them against the live remote at the moment of removal is planned for the step that applies a plan.

Plan, then apply

Scanning and planning are read-only. Today the plan is printed, as a summary or as JSON with --json, which you can save and read. In the design a plan is a file you edit and approve, and apply, when it exists, will do exactly that plan.

Everything removed will be findable

The design writes each removal to a manifest with a restore command. That part is planned, not built.

Download or build it

Once the maintainer publishes a release, prebuilt command-line programs are on the project's releases page. Each published release has one archive each for Linux (x86-64), macOS (Apple Silicon and Intel) and Windows (x86-64), plus a SHA256SUMS file. Tagging a version only prepares a draft, which the maintainer reads and then publishes by hand. If that page lists no release yet, there is nothing to download; build from source instead.

The programs are not signed

The archives are not code-signed or notarized. On macOS, Gatekeeper can refuse a program downloaded in a browser until you remove its quarantine mark. On Windows, SmartScreen can warn before it runs. Check the download first, as below, then follow the steps in the release notes.

Check what you downloaded

# the file matches the checksum list (Linux)
sha256sum -c --ignore-missing SHA256SUMS

# the file was built by this repository's release workflow for the tag vX.Y.Z
gh attestation verify <archive file name> --repo ericmacdougall/disk-cleaner --signer-workflow ericmacdougall/disk-cleaner/.github/workflows/release.yml --source-ref refs/tags/vX.Y.Z --deny-self-hosted-runners

Put the release's version, for example v0.1.0, in place of vX.Y.Z. A checksum shows the download is complete and matches the release page. The attestation, checked with the GitHub command-line tool, shows the file was built on a GitHub-hosted runner by this repository's release workflow for that version's tag. It does not show the code is free of bugs or that anyone reviewed it; that rests on the repository's rules and on the maintainer's publish step.

Build from source

You need a stable Rust toolchain and git. The README has the commands. The command is still called disk-cleaner until the planned rename.

The command is still called disk-cleaner today; renaming it to prunedisk is planned. The plan only describes what would happen. In the current version no command removes, moves or changes anything. The scanner writes a file only where you give --out.

Follow along

The project is developed in the open. The best way to follow it is the repository: the design document, the scanner's source and its scan format documentation, and the issue tracker. The repository is still named disk-cleaner; renaming the repository and the command to prunedisk is planned, not done. There is no mailing list, no account to create and no installer yet. Until a release is published you build the program from source; a published release is an archive holding the program, to unpack and run.
